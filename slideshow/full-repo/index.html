THE PITCH

A statistical simulator for single-elimination NBA-style tournaments: deterministic possession flow, heuristic outcome resolution — probabilities come straight from real player stats, no trained model.

THREE FACTS
  • Simulation is headless in the backend — one demo runs a full game in ~4 min
  • Broadcast UI is mock-powered today — live SSE is the next hop
  • Everything downstream reads one contract (2 files, 0–1 values)
The whole product is a chain: real statistics in, dramatic broadcast out. Data ingestion turns two external sources into two JSON files. The engine is a possession-level state machine whose probabilities come from those files — no ML. The output is a MatchLog that the broadcast renders. Keep this chain in mind — everything on the frontend and backend is a link in it.

Part I · The core idea · 0:50

Contract-first — one contract, all consumers

CATALOG CONTRACTdata_ingestion/schemas.py

Pydantic models for players.json / teams.json: Player, PlayerAttributes, Team. Imported by the engine, the DB seed, and the demo — nobody reads the files ad hoc.

MATCH CONTRACTengine/schemas.py

MatchLog → QuarterLog → PossessionLog → ActionLog, plus box scores and key moments — the only way the engine reports a match.

Why 0–1: an attribute is a probability. 0.58 two-pt → the engine rolls a random number against 0.58.
SAME CLASSES, EVERYWHERE

The DB stores attributes as a JSON column — file schema and database agree without a hard migration.
If you take one idea from this talk, take this: the contract. At the catalog level, the Pydantic schemas in data_ingestion define the two JSON files, and every consumer — engine, seed, demo — imports those same classes. At the match level, engine/schemas.py defines the MatchLog shape. The 0-to-1 normalization isn't cosmetic: an attribute is literally the probability the engine rolls against. And because the player attributes live in a JSON column, the file schema and the database stay in sync without migrations.

Part III · Engine: heuristics · 0:55

Possession state machine — probabilities, not rules

DECIDE: PASS · MOVE · SHOOT
if shot_clock <= 2.0:    return "SHOOT"
if shot_clock <= 7.0:    # urgency ramp
    p_shoot = 0.35 + 0.55 * (7 - shot_clock) / 7
else:
    p_shoot = 0.22
p_pass = (1 - p_shoot) * 0.52
p_move = (1 - p_shoot) * 0.48

Movement biases toward the opponent rim — the clock decides.

RESOLVE SHOT · heuristics.py
base = three_pt_pct if is_three else two_pt_pct
if stamina < 0.40:            # fatigue
    base -= (0.40 - stamina) * 0.25
if quarter >= 4 and |diff| <= 5: # clutch
    base += (clutch_factor - 0.5) * 0.12
is_made = rng.random() < clamp(base, 0.10, 0.95)
EVERY EXIT, DATA-DRIVEN
  • Pass turnover: clamp(turnover×0.7 + avg_steal×1.5, .04, .35)
  • Strip: clamp(turnover×0.5 + avg_steal, .03, .25)
  • Rebounds: all 10 players by rebound_rate — defense ≈ 75% norm
THE LOOP
while outcome == "continue":
    action = decide_handler_action(...)
    resolved = resolve(action)  # pass/move/shot
    clock.tick(action.duration_s)
# ends on basket · turnover · violation
# seeded rng → reproducible matches
The heart of the engine is a small state machine that loops a possession until a basket, turnover, or violation. Every decision is a weighted roll built from the player's real attributes: as the shot clock dies the shoot probability ramps; a shot's make probability is literally the player's two or three point percentage from the data, adjusted for fatigue below 40% stamina and boosted by clutch factor in tight late quarters. Passes and dribbles carry their own turnover risk from turnover and steal rates. The random generator is seeded, so any match can be replayed deterministically.

Now the data-processing stage inside the backend. Everything is deliberately split into two stages. Stage one touches the network: about thirty-nine polite calls to the NBA stats API, each saved verbatim to the raw folder — no processing ever. Basketball-Reference's classic positions need a one-time manual save because of Cloudflare. Stage two is pure offline pandas: it builds a master table, computes the twelve attributes, validates them against the schemas, and only then writes the final files. Because raw data is cached, re-running costs nothing; --no-fetch forces an offline run and fails fast if something's missing.
Part III · Data processing: the math · 0:50

Numbers → attributes — 12 values, all 0–1

SHOOTING (shrunk)
two_pt_pct = (2PM + 10·0.550) ÷ (2PA + 10)
three_pt_pct = league FG3_PCT, shrunk (0.360)
ft_pct = league FT_PCT, shrunk (0.783)

10 pseudo-attempts toward the league mean — a 1-for-1 player is ≈ league average, never 1.0.

POSSESSION & DEFENSE
usage_rate   = league USG_PCT (as-is)
turnover_rate= TOV ÷ used possessions
possessions  = FGA + 0.44·FTA + TOV   # ≈113.2/gm
defended     = team poss × min(min/48, 1)
foul/steal/block = per defended possession
PLAYMAKING & BOARD
rebound_rate = league OREB_PCT (as-is)
assist_rate  = AST ÷ teammate-made baskets
EFFORT & INTANGIBLES
stamina = minutes/game model − 0.5%/yr
          for age > 34     # config-tunable
clutch  = clutch FG% (last 5 min, close)
          vs season FG%   # boost, not raw stat
Shrinkage, worked: 6-for-6 (small sample) → (6 + 10·0.550) ÷ 16 = 0.72, not 1.00 · a 600-attempt star keeps ≈ his real number.
Quick tour of the formulas behind the twelve attributes — full detail lives in docs/statistics.md. Shooting percentages are shrunk with ten pseudo-attempts toward league averages, so small samples can't produce extremes. Usage and offensive-rebound rates reuse the league's own published columns. Defensive stats are computed per defended possession — a player's share of team possessions estimated from his minutes — so bench players don't inherit stats for defense they weren't on the floor for. Stamina is a minutes model with an age penalty; clutch measures how shooting changes in the last five minutes of close games. Consistent output: everything lands between zero and one.

The last step of the pipeline is the gate — the contract being enforced. Part IV · Decisions & risks · 0:45

Decisions we defend & risks we track

WE DEFEND
  • 0–1 attributes = probabilities — one mapping, zero conversion bugs
  • Shared schemas, not duplicated DTOs — engine imports ingestion schemas
  • Two-stage pipeline + verbatim cache — one network cost, reproducible re-derives
  • Gate before write — a broken pipeline beats a silently broken dataset
  • Heuristics over ML — statistics drive outcomes; explainable by construction
  • JSON attributes column — schema evolution without migrations
RISKS WE TRACK
  • Realism / calibration — do sims look statistically plausible? (SE-11)
  • Mock → live swap — the frame pipeline must survive SSE replacing the mock
  • Engine scope — fouls & free throws change the pace of the loop
  • No tests yet — the gate protects data, not services
  • LLM dependency — commentary quality gates Phase F
Trade-off we accepted: mock-first frontend buys a demo-able broadcast while the engine matures — the contract keeps the swap cheap.
A quick section on judgment calls. We defend the one-to-one probability contract, shared schemas everywhere, the two-stage pipeline with a verbatim cache, validating before writing, and heuristics instead of ML — every roll in the engine is explainable by the stat behind it. The risks we track: calibration and realism, the mock-to-live swap staying clean, engine scope like fouls changing pace, no tests, and LLM dependence. The trade-off we accepted is mock-first on the frontend — you can demo a broadcast today, and the contract is why swapping in a real engine later is cheap rather than a rewrite.

Backup · Possession math

A.1 — possession math, concretely

PER TEAM
possessions/game = Σ(FGA + 0.44·FTA + TOV) ÷ games
                  # 0.44 = NBA free-throw constant
                  # 2025-26 league: ≈ 113.2/game
PER PLAYER (defense)
defended_possessions =
    team_possessions × min(minutes ÷ 48, 1)

# bench steal rates aren't inflated by
# defense they weren't on the floor for
Backup: possession math. Team possessions per game are the classic estimator — sum of field goal, free throw (weighted 0.44) and turnover events, divided by games — about 113 per team per game in 2025-26. Defensive attributes divide by the player's defended possessions: his minutes share of team possessions, capped at full game. A bench player's steal rate never includes possessions he wasn't on court for.
Backup · Shrinkage

A.2 — shrinkage, worked

THE RULE
SHRINKAGE_K = 10   # config.py, tunable

value = (made + 10·league_rate) ÷ (attempted + 10)
WORKED · league 2pt ≈ 0.550
6-for-6   → (6 + 10·0.550) ÷ 16 = 0.72
             # not 1.00 — small sample
600 att @ 58% → ≈ 0.579
             # volume keeps the real number
Backup: shrinkage. Every shooting rate gets ten pseudo-attempts from the league mean, tunable in config.py. A player who went six-for-six sits at 0.72 instead of a mythical 1.00; a star with six hundred attempts keeps almost exactly his real rate. Same logic applies to three-pointers and free throws with their own league averages.
